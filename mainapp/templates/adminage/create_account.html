{% extends "base_shell_v2.html" %} {% comment %} Direction C · Registro. The in-app half of *who assigns a role, and where*. Until this page existed, onboarding any privileged user meant `manage.py createsuperuser`, the Django admin, and creating the Profile by hand — so the application could not make a professor at all, and `loginPage` answered a correct password with HTTP 500 for the account you had just half-created. **There is no administrator option and there must not be one.** `ProfileAdmin` keeps `role` writable only by a superuser, so a form here that could mint administrators would hand every administrator session the escalation that constraint exists to withhold. The second administrator comes from `manage.py create_administrator`, where the gate is shell access rather than a cookie. The «Rol» help text says so on the page, because someone looking for the missing option deserves to be told where it went rather than left to conclude the app is broken. One POST form, no cascade — the same reasoning as `create_and_assign_student`, and for a sharper reason: a GET round trip to narrow the identity control by role would put a password in the query string. All three identity controls render at once and the form's `clean()` enforces the one the chosen role needs. Nothing here depends on JavaScript, so nothing degrades without it. The two counts above the form are the page stating what it can actually do before anyone types a password — the same argument as `no_other_destination` on `reassign_students`. A control that cannot do anything must say which of the two it is. {% endcomment %} {% block page_title %}Alta de cuenta{% endblock page_title %} {% block breadcrumb %}Administración / Alta de cuenta{% endblock breadcrumb %} {% block main %}
